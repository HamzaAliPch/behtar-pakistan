# Phase 4A: citizen notifications and case targets

## Architecture

- Existing `Notification` rows remain the in-app inbox. New case notices use an event-derived unique key, so retrying a transaction cannot create a second copy. Complaint ownership always uses `Complaint.userId`, including citizens whose role later becomes `VOLUNTEER`.
- `NotificationOutbox` stores opt-in external work and scheduled resolution reminders. `NotificationDeliveryAttempt` records each outcome and a safe error code. Claims use a conditional status/attempt update; stale claims can be retried after 15 minutes. Attempts are bounded to three. The worker processes at most 50 due rows per invocation and limits each user/channel to five deliveries per hour.
- SMS and WhatsApp are **disabled** by default. The only implemented adapter is a no-network QA mock, allowed only under `FRIEND_TEST_MODE=1` or `AUTH_TEST_MODE=1`. An unconfigured adapter records `BLOCKED/provider_unconfigured`; it never reports a successful send. A real provider adapter, credentials, legal/consent review and separate live tests are still required.
- Opt-in preferences and optional mobile number live in `CitizenProfile`. External messages are queued only for a valid Pakistan mobile number and enabled channel. The worker rechecks consent and contact before each attempt. Opting out cancels pending work. Messages contain only a case reference, short generic update, and a link to the authenticated tracking page; no location, evidence or private case text is sent.
- A proposed resolution creates an immediate owner notification plus up to two scheduled reminders. `RESOLUTION_REMINDER_HOURS` defaults to `24,72` and accepts at most two valid hour values. Confirmation, dispute or a transition away from proposal cancels remaining reminders. The worker never changes complaint status or publication.
- The webhook endpoint is disabled by default. When a future provider is integrated, it requires a configured 32-character minimum secret, HMAC-SHA256 over timestamp and body, a five-minute timestamp window, a 4 KB size limit and a unique event ID. It accepts callbacks only for rows explicitly awaiting a webhook. Current adapters never enter that state, so this route cannot claim a real delivery today.
- `SlaPolicy` has an approved, versioned target for an active city and category (with an optional `ALL` fallback). Approval is restricted to administrators and audited. A new complaint receives a `ComplaintSlaSnapshot` at submission, including the selected policy version and UTC target dates. No policy means null targets. Earlier complaints and snapshots are not rewritten when a policy changes. First review, verification/assignment and proposal milestones are recorded once. Citizen tracking and the admin SLA workspace display dates in `Asia/Karachi`; goals are explicitly not guarantees.

## Operations

Apply migration `20260928120000_notifications_sla` with `prisma migrate deploy`. It adds fields and tables without deleting or rewriting historical rows. The main and friend-test databases were backed up locally before migration. No historical complaint receives an invented target.

Migration `20260928130000_notification_worker_state` adds a singleton lease and last-run record. `npm run notifications:work` performs one bounded run. `npm run notifications:serve` is a recurring process; `NOTIFICATION_WORKER_INTERVAL_MINUTES` defaults to five (valid range 1–60). Run **one** recurring instance under a process supervisor. The database lease also prevents overlapping invocations, expires after 20 minutes for crash recovery, and individual stale outbox claims recover after 15 minutes. `/admin/sla` shows observed last success, result and lease state. It does not imply an OS service is installed.

For local Windows testing, open a dedicated PowerShell terminal in the project, dot-source `scripts/friend-test-env.ps1`, set `NOTIFICATION_PROVIDER_MODE=disabled`, then run `npm run notifications:serve`. Stop it with Ctrl+C. A Windows Task Scheduler option is a five-minute trigger that invokes `npm run notifications:work` with a reviewed working directory and environment; never point it at the main database by accident. For production, use a supervised one-shot five-minute job or a supervised recurring process with `NOTIFICATION_WORKER_ENABLED=1` and the correct environment. The scheduler needs persistent process supervision and monitoring; app HTTP requests do not run reminders. The isolated friend-test recurring process was observed completing multiple one-minute QA cycles; this does not prove a production scheduler exists.

Keep `NOTIFICATION_PROVIDER_MODE=disabled` until a real adapter has been implemented and separately authorized. `mock` is no-network and only accepted in friend/auth-test mode. Unknown modes fail closed. The adapter interface carries a stable outbox idempotency key for a future provider. An approved SMS/WhatsApp provider must support idempotent sends or reconciliation, signed callback verification, channel-specific opt-in/template rules, credential storage and live consent testing before enabling. Current signed callback handling remains disabled and cannot falsely mark sends delivered. Configure `NOTIFICATION_PUBLIC_ORIGIN` to the approved HTTPS site before any external adapter is enabled. Never place provider credentials in source or screenshots.

Password recovery uses the existing HTTPS reset-link origin and one transactional-email abstraction. Its original HTTPS relay remains available when `PASSWORD_RESET_DELIVERY_URL`, `PASSWORD_RESET_DELIVERY_SECRET` and `PASSWORD_RESET_PUBLIC_ORIGIN` are valid. Namecheap Private Email SMTP is an optional production transport selected with `NOTIFICATION_PROVIDER_MODE=smtp` and the private `SMTP_*` settings in `docs/namecheap-stellar-rc1.md`. Friend/auth-test mode always disables live delivery. The owner must test actual mailbox receipt before enabling the reset form in production.

The profile page shows opt-in switches, channel availability and owner-only delivery history. `/notifications` remains the in-app inbox. `/admin/sla` approves future targets, lists approaching/overdue active cases and shows delivery status counts and blocked error codes without contacts or message content; the admin overview links to those counts. `/track` shows owner-only target snapshots and an accessible case timeline. Anonymous and unrelated users keep the existing public-safe status view.

## Verification and current limits

The `auth-test.db` suite covers idempotent notice creation, opt-in and invalid contacts, mock retry, disabled-provider behavior, a signed/replayed webhook, volunteer submitter ownership, reminder cancellation, target calculations, unchanged historical targets and existing publication/privacy gates. Friend-test browser checks used a temporary fictional citizen and cleaned it up afterward: saved preferences, read an in-app notification, blocked unrelated SLA access, showed an owner’s undefined legacy target, and saved a temporary admin policy before removing it. No external message was queued by that profile check. No real SMS or WhatsApp send has been made or verified.

Existing legacy cases have no SLA snapshot unless a team member defines a carefully reviewed historical backfill; they display “Target not yet defined.” The admin attention list shows at most 500 active snapshots, so a larger deployment should paginate and aggregate this query. A live provider adapter and scheduled worker are required for external reminders. The temporary external test hostname still needs verified Cloudflare Access before inviting testers; Phase 4A does not change Cloudflare settings.
