## Security and privacy checklist

- **PASS, code and tests:** password hashing; database-backed login throttling; seven-day server-side sessions using random tokens with stored hashes; production HTTP-only, Secure, SameSite=Lax host-only cookie; complaint ownership bound to `Complaint.userId`, including citizen-plus-volunteer; admin and city-role checks; unrelated-user tracking isolation; owner-only confirmation.
- **PASS, code and tests:** private media authorization, signature/type/size checks for uploaded photos and field video, random private storage keys, no upload directory in `public/`; approved public map markers use approximate coordinates and separate approval; pin-less story publication retains citizen confirmation, summary and image approval gates.
- **PASS, code and tests:** notification recipient ownership, opt-in recheck, bounded outbox retries and cancellation; duplicate-link admin authorization and independent case ownership/SLA/status; password-reset tokens are short-lived and single-use in the test harness.
- **DISABLED:** friend-test donation collection; real SMS/WhatsApp delivery; reset-email delivery; notification webhook; real government submission integration. The only external-message adapter available is a no-network QA mock, and the current test configuration does not activate a real provider.
- **LIMITATION:** public request throttling in some routes uses process memory and is not a distributed control. Production reverse-proxy rate limiting and trusted client-IP handling need review. The main environment defaults to `dev.db` and `private_uploads` if not overridden; production must use an explicit, separately checked configuration. No production secret store or host allowlist was verified.
- **BLOCKER:** friend-test public figures include `[QA TEST]` data (at baseline, 4 of 5 public map cases and 3 of 4 published stories are QA-labeled). Never deploy or promote this database/uploads as civic impact. A fresh production database, approved genuine content and a separate production funds ledger are required.

## Release gates and owner decisions

1. Record an immutable source revision or reviewed source archive, then rerun build/tests against that exact revision.
2. Approve hosting, persistent database/media storage, backups and operating costs. Create production-only paths and secrets; do not copy `dev.db`, `friend-test.db`, `auth-test.db` or any QA uploads.
3. Verify Cloudflare Access for the temporary test site from a fresh unauthenticated browser before inviting anyone; separately approve final production DNS, HTTPS and access policy. No Cloudflare setting was changed here.
4. Install and monitor a supervised web process and a single scheduled notification worker. Keep provider mode disabled until a separately approved, consent-reviewed integration is tested live.
5. Keep payment collection disabled until legal status, receiving accounts, independent verification process and public fundraising launch are approved. Do not treat a draft referral as a government submission.
6. Review the informational navigation/draft-persistence limitations if they matter for launch, and perform a final production-origin privacy/restore drill on non-live data.

**Decision:** RC1 is **BLOCKED for public launch** by missing production isolation/operations and the possibility of presenting friend-test QA figures as real impact. The application candidate passes the local and isolated functional gates listed above.
